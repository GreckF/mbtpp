MoonBit++ Manual

The MoonBit++ Manual

MoonBit++ is a dependently typed language with MoonBit syntax: the same fn, enum, struct, trait, match, let mut, for, and raise, plus dependent types, indexed types, dependent pattern matching, propositions, and proofs.

It includes:

  • A type checker: dependent types, unification, dependent pattern matching with coverage checking, instance search, and simple tactics.
  • An interpreter: runs type-checked programs directly.
  • A compiler: translates programs to MoonBit, generating native code for the parts expressible in MoonBit types.
  • moonpp: a moon-like command-line tool for managing projects, dependencies, and builds.

This is a purely vibe-coded fun project. Please don’t take it seriously.

This manual has three parts:

  • Language: one chapter per feature, from lexical structure to proofs, traits, and effects.
  • moonpp: installation, project layout, commands, dependencies, and build output.
  • Interop with MoonBit: importing MoonBit packages, compiling to MoonBit, #mbt declarations, and using compiled output from MoonBit.

Examples with fn main have a ▶ button in the top-right corner that opens them in the Playground to run. Source code and examples are on GitHub.

Quick Start

After installing moonpp (see Installation):

moonpp new hello
cd hello
moonpp run                # run src/main with the interpreter
moonpp check              # type check
moonpp run --compiled     # compile to MoonBit, then run
moonpp build              # compile into the MoonBit project mbtpp_out/main

The src/main/main.mbtpp generated by moonpp new looks like this:

enum Vector[T] : Nat -> Type {
  Nil : Vector[T](0)
  Cons[n : Nat](T, Vector[T](n)) : Vector[T](S(n))
}

// Accepts only non-empty vectors: no Nil branch needed
fn[T, n : Nat] Vector::head(self : Vector[T](S(n))) -> T {
  match self {
    Cons(x, _) => x
  }
}

fn main {
  let v : Vector[String](2) = Cons("Hello", Cons("MoonBit++", Nil))
  println(v.head())
}
  • Vector[T](n) is a vector of length n: T is a parameter and n is an index (see enum and indexed types).
  • head only accepts vectors of type Vector[T](S(n)), so Nil cannot occur and the match needs no branch for it (see Coverage checking and impossible branches).
  • v.head() calls the method Vector::head.

You can also try it without installing anything in the Playground.

Lexical Structure

  • Comments: // … to the end of the line. There are no block comments.
  • Identifiers: letters, digits, and _, not starting with a digit. By convention, types, constructors, and traits start with an uppercase letter; everything else is lowercase.
  • Statement separators: newline or ;.

Expressions and Statements

Expressions and statements are the same as in MoonBit:

fn demo(xs : Array[Int]) -> Int {
  let a = 1                       // immutable binding
  let mut total = a               // mutable binding
  total = total + 2               // assignment
  for x in xs {
    total = total + x
  }
  let f = (x : Int) => x * 2      // lambda; also x => e, (x, y) => e
  let g = fn(x : Int) { x + 1 }   // anonymous function
  let s = if total > 10 { "big" } else { "small" }
  println(s)
  total |> f |> g                 // pipe
}

fn main {
  println(demo([1, 2, 3]))
}
  • Blocks: the value of { s1; s2; e } is the last expression.
  • let: let x = e, let x : T = e; pattern bindings let (a, b) = pair (coverage checked).
  • if: if c { a } else { b } is an expression; without else its value is ().
  • Lambdas: x => e, (x, y) => e, (x : Int) => e, fn(x : Int) { … }.
  • Pipes: e |> f means f(e), and e |> f(a) means f(e, a).
  • Type annotations: (e : T).
  • Holes: _ is inferred by unification and can appear in both expressions and types, e.g. Cons(_, xs), f[_, Int](x).
  • Local functions: a block can contain fn name(x : T) -> R { … }; it can be recursive. A recursive local function cannot use the let mut variables around it.
  • Cascades: xs..push(1)..push(2) calls the methods of xs in turn; its value is xs.
  • Arrays: xs[i] reads an element and xs[i] = v assigns one.

There are three kinds of equals sign: = defines, == is boolean equality (result Bool), and === is propositional equality (result Prop; see Propositional equality).

For loops, return, break, and continue, see Mutable state and loops; for raise and try, see Error handling.

Functions

fn add(x : Int, y : Int) -> Int {
  x + y
}

fn[T] twice(f : (T) -> T, x : T) -> T {   // [T]: implicit parameter
  f(f(x))
}

fn answer() -> Int { 42 }                 // function with no parameters

fn main {
  println(add(1, 2))
  println(twice(x => x + 1, 0))
  println(twice[Int](x => x * 2, 1))      // pass the implicit parameter explicitly
  println(answer())
}

No currying

A function takes a group of parameters: (Int, Int) -> Int takes two parameters and is a different type from (Int) -> (Int) -> Int, which returns a function. Partial application is not allowed.

A function with no parameters (fn answer()) is represented internally as taking a single Unit parameter.

Implicit parameters

Implicit parameters go in [...] after fn:

fn[T] count(xs : Array[T], extra : Nat) -> Nat {
  plus(xs.size(), extra)
}

fn main {
  println(count([1, 2], 3).to_int())
}
  • [T] means [T : Type]. For an implicit parameter without a type, the type is inferred from its uses, defaulting to Type if it cannot be inferred.
  • At call sites they are usually inferred by unification. You can also give them positionally with f[a, b](x): you may give only a prefix, and you may write _.
  • Implicit parameters can only be written after fn; fn f[T](...) is not supported.

Other forms

  • Methods: fn Type::m(self : Type, …); see Methods and operators.
  • Labelled arguments: x~ : T, x? : T; see Labelled arguments.
  • lemma: a function whose result is a proposition; see lemma.
  • External primitives: fn f(x : Int) -> Int = "%prim_name", used only in the Prelude.
  • main: fn main { … }, the program entry point.

Methods and Operators

Methods

fn Type::m(self : Type, …) defines a method on type Type. x.m(a) calls T::m(x, a), where T is the head of x’s type; you can also write Type::m(x, a).

enum Color {
  Red
  Green
}

fn Color::name(self : Color) -> String {
  match self {
    Red => "red"
    Green => "green"
  }
}

fn main {
  println(Red.name())
  println(Color::name(Green))
}

x.m() looks for the type’s own methods first, then trait methods (see trait).

Types

Universes

  • Type : Type: types are values, and the type of a type is Type (which makes the system inconsistent; see the disclaimer in the introduction).
  • Prop : Type: the universe of propositions. Values of types in Prop are proofs; proofs are irrelevant, so any two proofs of the same type are considered equal. See Propositions and proofs.

Application and shorthands

  • Types are functions too: Array[Int], Vector[T](n), and Id[T](x)(y) are all ordinary applications, where [...] gives implicit arguments and (...) gives explicit ones.
  • T? means Option[T]; (A, B) is a pair type.
  • A function returning Type is a type-level function; see Type-level computation.

Constants and type aliases

  • const N : Int = 3 and const N = 3 define constants (like let).
  • typealias Int as Score and typealias Pair[A] = (A, A) define type aliases.

Type-Level Computation

Types are values, so you can compute types with ordinary functions, and the type checker normalizes (evaluates) them:

// The type of functions that take n Int arguments and return Int
fn NAry(n : Nat) -> Type {
  match n {
    Z => Int
    S(k) => (Int) -> NAry(k)
  }
}

fn sum_n(n : Nat, acc : Int) -> NAry(n) {
  match n as m return NAry(m) {
    Z => acc
    S(k) => x => sum_n(k, acc + x)
  }
}

fn main {
  println(sum_n(3, 0)(1)(2)(3))   // 6
}

The type of sum_n(3, 0), NAry(3), is computed during type checking to (Int) -> (Int) -> (Int) -> Int. Here a return clause gives the motive of the match.

During type checking, pure functions are unfolded, and functions that use mutable state, loops, or exceptions are run, staying folded when the run cannot finish (see Mutable state and loops).

Time limits

There is no termination checking, so a computation during type checking may never end. The checking of each definition is therefore limited in time, 30 seconds by default; beyond that, the definition fails, with the function being evaluated at that moment:

t.mbtpp:3:1: error: checking f took more than 30 s (while evaluating T); a definition that does
not terminate? Raise the limit with #timelimit(seconds) or #timelimit(none)

#timelimit before a definition changes its limit:

fn sum_to(n : Int) -> Int {
  let mut acc = 0
  for i = 1; i <= n; i = i + 1 {
    acc = acc + i
  }
  acc
}

#timelimit(120)
lemma big : sum_to(1000) === 500500 = Refl

#timelimit(none)
lemma bigger : sum_to(2000) === 2001000 = Refl
  • The unit is seconds; #timelimit(none) means no limit. It can be combined with #mbt.
  • The limit applies to each definition, not to the whole check. The signature and the body are timed separately. Other definitions checked on the way (for example functions it uses that are written later) have their own limits, and their time does not count for this one.
  • The limit only covers type checking, not running the program with moonpp run.
  • The playground also stops a whole check or run after 60 seconds, and the VS Code extension stops a check after 120 seconds by default (setting mbtpp.checkTimeout).

enum and Indexed Types

Plain enums

enum Shape {
  Circle(Double)
  Rect(Double, Double)
}

fn Shape::area(self : Shape) -> Double {
  match self {
    Circle(r) => 3.14 * r * r
    Rect(w, h) => w * h
  }
}

fn main {
  println(Rect(2.0, 3.0).area())
}

Parameters and indices

enum Name[implicit params](explicit params) : indices -> universe { constructors }
  • Parameters come after the name and are fixed across all constructors.
  • Indices come after the colon and may vary between constructors. The universe is Type or Prop.
  • Constructors: C[own implicit params](fields) : return type. The return type can be omitted when there are no indices.
enum Vector[T] : Nat -> Type {
  Nil : Vector[T](0)
  Cons[n : Nat](T, Vector[T](n)) : Vector[T](S(n))
}

// Indices written in []: a GADT
enum Exp : [T] -> Type {
  IntLit(Int) : Exp[Int]
  BoolLit(Bool) : Exp[Bool]
  Add(Exp[Int], Exp[Int]) : Exp[Int]
  If[T](Exp[Bool], Exp[T], Exp[T]) : Exp[T]
}

fn[T] Exp::eval(self : Exp[T]) -> T {
  match self {
    IntLit(n) => n
    BoolLit(b) => b
    Add(l, r) => l.eval() + r.eval()
    If(c, t, f) => if c.eval() { t.eval() } else { f.eval() }
  }
}

fn main {
  let e = If(BoolLit(true), Add(IntLit(1), IntLit(2)), IntLit(0))
  println(e.eval())
}

The result type of Exp::eval varies by constructor: when IntLit(n) matches, T is refined to Int.

Named fields

Constructor fields can be named, and the types of later fields can refer to them:

enum Sigma[A](P : (A) -> Type) {
  MkSigma(fst : A, snd : P(fst))
}

Using constructors

  • The data type’s parameters are always inferred; [...] supplies only the constructor’s own implicit parameters, e.g. Cons[n](x, xs).
  • Constructors with the same name are disambiguated by the expected type, or you can write the full name Vector::Cons.
  • An enum whose universe is Prop is a proposition, e.g. Id in the Prelude (see Propositional Equality).

Labelled fields

enum Shape {
  Rect(width~ : Int, height~ : Int)
  Circle(Int, label~ : String)

fn area(s : Shape) -> Int {

Constructor fields can have labels: C(x=e) builds, and C(x~) or C(x=p) matches; .. lets the other fields match anything.

struct and Dependent Fields

struct Point {
  x : Int
  y : Int
}

fn main {
  let p : Point = { x: 1, y: 2 }
  println(p.x + p.y)
}
  • Construction: { x: 1, y: 2 }; the type is determined by the expected type.
  • Field access: p.x.
  • Parameters: struct Name[T, n : Nat] { … }.
  • Struct patterns ({ x: a, y: b } => …) are not supported; use field access.

Dependent fields

Later fields can depend on earlier ones, e.g. an array that carries a proof of its length:

struct Vec[T, n : Nat] {
  to_array : Array[T]
  length_to_array : to_array.size() === n
}

fn[T] Vec::from_array(xs : Array[T]) -> Vec[T, xs.size()] {
  { to_array: xs, length_to_array: Refl }
}

fn[T, n : Nat] Vec::get(self : Vec[T, n], i : Int) -> T {
  self.to_array[i]
}

fn main {
  let v = Vec::from_array([1, 2, 3])
  println(v.get(1))
}

xs.size() returns a Nat, so it can appear in types; xs.length() returns an Int.

Mutable fields, updates, patterns and tuple structs

struct Counter {
  name : String
  mut count : Int
}

struct Pair(Int, Int)

struct Point {
  x : Int
  y : Int
} derive(Show)

fn main {
  let c = { name: "clicks", count: 0 }
  c.count += 1
  let copy = { ..c, name: "copy" }
  copy.count = 10
  println("\{c.count} \{copy.count}")
  match Pair(1, 2) {
    Pair(a, b) => println(a + b)
  }
  let p = { x: 3, y: 4 }
  match p {
    { x, .. } => println(x)
  }
  println({ ..p, y: 10 })
}
  • mut fields: p.x = v and p.x += 1 change them, and every reference to the same struct sees the change.
  • Updates: { ..p, x: e } is a new struct whose other fields come from p (mut fields get a copy of their current value).
  • Patterns: { x, y }, { x: p, .. }; omitting fields requires ... In a pattern, a mut field can only be _.
  • Tuple structs: the fields of struct P(Int, Int) are 0 and 1; P(a, b) builds one and is its pattern. type Meters Int is a tuple struct with one field.
  • mut fields take no part in type-level computation; the mut fields of structs imported from MoonBit can only be read.

Pattern Matching

match is written the same way as in MoonBit:

fn describe(n : Int, xs : List[Int]) -> String {
  match (n, xs) {
    (0, _) => "zero"
    (_, Nil) => "empty"
    (_, Cons(x, Cons(_, _))) => "at least two, starting with \{x}"
    _ => "other"
  }
}

fn main {
  println(describe(1, Cons(7, Cons(8, Nil))))
}
  • Patterns: variables, the wildcard _, constructors (possibly nested), literals, tuples.
  • Arms are tried in order and may overlap; the first matching arm wins.
  • Implicit parameters of constructors can be bound or ignored in patterns: If[t](c, a, b), IZ[_, a] => a.
  • let patterns: let (a, b) = pair.

Or-patterns, as, and guards

enum Shape {
  Circle(Int)
  Rect(Int, Int)
  Square(Int)
}

fn kind(s : Shape) -> String {
  match s {
    Rect(_, _) | Square(_) => "polygon"
    Circle(r) if r > 10 => "big circle"
    Circle(_) => "circle"
  }
}

fn widest(s : Shape) -> Shape {
  match s {
    Rect(w, _) | Square(w) as big if w > 100 => big
    other => other
  }
}

fn main {
  println(kind(Circle(11)))
  println(widest(Square(200)) is Square(_))
}
  • Or-patterns p | q can be nested (Some(1 | 2)); all alternatives must bind the same variables. The checker expands them into separate arms, each matched dependently on its own.
  • p as x: x is the whole matched value. as binds loosest: in A | B as x, x is the value matched by A | B.
  • Guards p if cond => …: when the condition is false, the following arms are tried. The condition can use the variables bound by the pattern. Guarded arms do not count for coverage.

Array and range patterns

fn describe(xs : Array[Int]) -> String {
  match xs {
    [] => "empty"
    [x] => "one: \{x}"
    [a, .. rest, z] if a == z => "same ends around \{rest.length()}"
    [a, ..] => "starts with \{a}"
  }
}

fn kind(c : Char) -> String {
  match c {
    'a'..='z' => "lower"
    '0'..='9' => "digit"
    _ => "other"
  }
}

fn main {
  println(describe([3, 1, 2, 3]))
  println(kind('q'))
}
  • Array patterns: [p, q] matches exactly two elements, [p, .., z] at least two; ..rest binds the elements in between, as a new array. They also match a String (its elements are Chars).
  • Range patterns: lo..=hi and lo..<hi between literals; _ leaves a bound open, as in _..<60.
  • Range patterns become guards, so the match stays dependent. A match with array patterns tests its arms one after another: it is not checked for coverage (when no arm applies, the program aborts) and does not refine types. So is a match with is in a guard; the variables bound by that is are visible in the arm.

is and guard

fn get(o : Option[Int]) -> Int {
  if o is Some(x) && x > 5 {
    x
  } else {
    0
  }
}

fn length(xs : List[Int]) -> Int {
  let mut cur = xs
  let mut n = 0
  while cur is Cons(_, rest) {
    n = n + 1
    cur = rest
  }
  n
}

fn head_or(xs : List[Int], d : Int) -> Int {
  guard xs is Cons(h, _) else { return d }
  h
}

fn main {
  println(get(Some(9)))
  println(length(Cons(1, Cons(2, Nil))))
  println(head_or(Nil, 42))
}
  • e is p is a Bool. In the condition of an if, while or guard, the variables bound by p are visible in the rest of the && chain and in the code run when the condition holds.
  • guard cond else { … }: when the condition fails, the else block runs; it usually returns, breaks or calls abort(…). The following statements can use the variables bound by cond. Without else, a failed condition aborts the program.
  • With is in a condition, the else branch is expanded once at each is that can fail, so its code is duplicated.

Pattern matching in MoonBit++ is dependent:

  • Dependent Matching and Refinement: matching a constructor refines the indices in types.
  • Coverage Checking and Impossible Branches: missing arms are errors, and arms that are impossible by their types can be omitted.
  • The return Clause: give the motive of a match explicitly (Rocq style).

Dependent Matching and Refinement

When you match on a variable, the constructor’s indices are unified with the indices in the variable’s type, and the result refines the whole context and the goal type (Agda style):

enum Vec2[T] : Nat -> Type {
  VNil : Vec2[T](0)
  VCons[n : Nat](T, Vec2[T](n)) : Vec2[T](S(n))
}

fn[T, n : Nat] Vec2::zip_with(self : Vec2[T](n), other : Vec2[T](n), f : (T, T) -> T) -> Vec2[T](n) {
  match (self, other) {
    (VNil, VNil) => VNil
    (VCons(x, xs), VCons(y, ys)) => VCons(f(x, y), xs.zip_with(ys, f))
  }
}

fn main {
  let v : Vec2[Int](2) = VCons(1, VCons(2, VNil))
  match v.zip_with(v, (a, b) => a + b) {
    VCons(x, _) => println(x)
  }
}
  • When self matches VNil, unification yields n = 0. So other : Vec2[T](0) can only be VNil, and combinations like (VNil, VCons(…)) need not be written.
  • In each arm the goal type Vec2[T](n) is refined too: the VNil arm returns Vec2[T](0), and the VCons arm returns Vec2[T](S(n')).
  • Matching on implicit parameters refines as well, e.g. match g { Empty => …; Extend(_, _) => … }, where g is an implicit parameter of the function.

Matching on the result of a function call

When the scrutinee is not a variable (e.g. a function call), the index relationships in its result type are still used to refine the goal type:

match progress(t1) {
  PrStep(_, u1, st1) => PrStep(_, _, StApp1(t1, u1, t2, st1))
  PrDone(_, VLam(b)) => PrStep(_, _, StApp(b, t2))
}

See examples/stlc.mbtpp in the repository for the full example.

Eliminating Prop

When matching on data in Prop, the result must also be in Prop, unless the type is a subsingleton (such as propositional equality ===, which has at most one proof).

Coverage Checking and Impossible Branches

Every match must cover all cases; otherwise it is an error:

t.mbtpp:2:3: error: match is not exhaustive; missing case(s):
  S(_)

Impossible branches

When a constructor’s indices fail to unify with the scrutinee’s type, that branch cannot occur and can be omitted:

enum Fin : (Nat) -> Type {
  FZ[n : Nat] : Fin(S(n))
  FS[n : Nat](Fin(n)) : Fin(S(n))
}

enum Vector[T] : Nat -> Type {
  Nil : Vector[T](0)
  Cons[n : Nat](T, Vector[T](n)) : Vector[T](S(n))
}

// No Nil arm needed: Fin(0) is empty, so Nil can never occur together with a Fin(n)
fn[T, n : Nat] Vector::get(self : Vector[T](n), i : Fin(n)) -> T {
  match (self, i) {
    (Cons(x, _), FZ) => x
    (Cons(_, xs), FS(j)) => xs.get(j)
  }
}

fn main {
  let v : Vector[String](3) = Cons("a", Cons("b", Cons("c", Nil)))
  println(v.get(FS(FS(FZ))))
}

You can also write just the pattern without =>; the checker then confirms that it really is impossible (if it is not, it reports “this pattern is not impossible”):

enum V3[T] : Nat -> Type {
  N3 : V3[T](0)
  C3[n : Nat](T, V3[T](n)) : V3[T](S(n))
}

fn[T, n : Nat] V3::head(self : V3[T](S(n))) -> T {
  match self {
    N3
    C3(x, _) => x
  }
}

Empty types

A type that no constructor can match is empty, and a match on it may have no arms. The checker also recognizes empty types in nested positions; for example, a constructor with a field of type Fin(0) need not be listed. Built-in types (Int, Array, etc.) are not empty.

The return Clause

match e as x in D[_](i) return P(i, x) { … }

A Rocq-style match: you give the motive P explicitly, i.e. how the result type of each arm depends on the scrutinee x and its index i.

enum Vector[T] : Nat -> Type {
  Nil : Vector[T](0)
  Cons[n : Nat](T, Vector[T](n)) : Vector[T](S(n))
}

fn[T, n : Nat] Vector::length_eq(self : Vector[T](n)) -> Nat {
  match self as v in Vector[_](m) return Nat {
    Nil => Z
    Cons(_, xs) => S(xs.length_eq())
  }
}

fn main {
  let v : Vector[Int](2) = Cons(7, Cons(8, Nil))
  println(v.length_eq().to_int())
}
  • as x names the scrutinee, in D[_](i) names the indices in its type, and return P is the motive; each of the three parts can be omitted (as in match n as m return NAry(m) in Type-Level Computation).
  • With return, Rocq semantics apply and the context is not refined; without return, the match works as described in Dependent Matching and Refinement.

Propositions and Proofs

Propositions are types in Prop, and proofs are their values. The type checker computes (normalizes) expressions while checking proofs, so many equalities follow directly by computation.

  • Propositional Equality: ===, Refl, and the equality lemmas in the Prelude.
  • lemma: declaring theorems.
  • Tactics: building proofs step by step with proof { … }.

User-defined propositions are enums whose universe is Prop:

enum And[A : Prop, B : Prop] : Prop {
  Conj(A, B)
}

lemma and_comm[A : Prop, B : Prop](p : And[A, B]) -> And[B, A] {
  match p {
    Conj(a, b) => Conj(b, a)
  }
}

There is no termination checking and no strict positivity checking: recursive functions and recursive proofs are accepted as they are, so false propositions can be “proved”.

Propositions are proof irrelevant: two proofs of a proposition are equal, and a proof is eliminated only into a proposition, or into any type when the proposition is a subsingleton (at most one constructor, whose fields are proofs, like ===). So no value depends on a proof, and all proofs are erased at compile time (see Compiling to MoonBit). A cast with a false proof (Id::subst) does not hang in a compiled program on the infinite recursion; it fails at run time where the types do not match.

Propositional Equality

a === b is Id[_](a)(b) from the Prelude:

enum Id[T](x : T) : (y : T) -> Prop {
  Refl : Id[T](x)(x)
}

Refl is the only constructor, and it proves x === x. Because type checking computes, any equality whose two sides normalize to the same term can be proved directly with Refl:

lemma two_plus_two : (2 : Nat) + 2 === 4 = Refl

lemma plus_zero_left(n : Nat) -> (0 : Nat) + n === n {
  Refl
}

0 + n computes to n by the definition of Nat::op_add; n + 0 cannot be computed directly (n is a variable) and needs induction; see lemma.

Equality lemmas

LemmaType
Id::sym(p)from x === y derive y === x
Id::trans(p, q)from x === y and y === z derive x === z
Id::cong(f, p)from x === y derive f(x) === f(y)
Id::subst(p, motive, px)from x === y and motive(x) derive motive(y); motive may return Type

=== is a subsingleton, so you can match on Refl to rewrite types, even when the result is in Type:

fn[a : Nat, b : Nat] cast(e : a === b, xs : Array[Int]) -> Array[Int] {
  match e {
    Refl => xs
  }
}

== is not the same as ===: == compares values, producing a Bool that can be computed at run time; === is a proposition.

lemma

A lemma is the same as a fn, except that its result is usually a proposition. There are two forms:

  • lemma name[implicits](params) -> proposition { proof }
  • lemma name[implicits] : proposition = proof expression

Induction is done with pattern matching and recursion:

lemma plus_zero(n : Nat) -> n + 0 === n {
  match n {
    Z => Refl
    S(k) => Id::cong(S, plus_zero(k))
  }
}

lemma plus_succ(n : Nat, m : Nat) -> n + S(m) === S(n + m) {
  match n {
    Z => Refl
    S(k) => Id::cong(S, plus_succ(k, m))
  }
}

lemma append_nil[T](xs : List[T]) -> xs.append(Nil) === xs {
  match xs {
    Nil => Refl
    Cons(x, rest) => Id::cong(r => List::Cons(x, r), append_nil(rest))
  }
}
  • In the Z arm, both sides of the goal 0 + 0 === 0 compute to the same term, so Refl works.
  • In the S(k) arm, the goal is S(k) + 0 === S(k), which computes to S(k + 0) === S(k); it follows from the recursively obtained k + 0 === k via Id::cong(S, …).
  • The recursive call is the induction hypothesis. The checker does not verify that the recursion terminates.

For longer proofs, see examples/proofs.mbtpp in the repository (associativity of vector append, properties of reverse) and examples/stlc.mbtpp (substitution lemmas, progress, and canonicity for the simply typed λ-calculus, plus an evaluator extracted from the canonicity proof).

Tactics

proof { … } builds a proof step by step with tactics, one per line:

lemma plus_zero(n : Nat) -> n + 0 === n {
  match n {
    Z => Refl
    S(k) => Id::cong(S, plus_zero(k))
  }
}

lemma plus_succ(n : Nat, m : Nat) -> n + S(m) === S(n + m) {
  match n {
    Z => Refl
    S(k) => Id::cong(S, plus_succ(k, m))
  }
}

lemma plus_comm : forall n m : Nat, n + m === m + n = proof {
  intros n m
  destruct n
  rewrite plus_zero(m)
  rfl
  rewrite plus_succ(m, n_0)
  rewrite plus_comm(n_0, m)
  rfl
}

rflClose the goal with Refl (both sides normalize to the same term)
destruct xCase split on x, one new goal per constructor; fields are named x_0, x_1, … (also cases)
rewrite e, rewrite <- eRewrite the goal with the equality e, left to right or right to left (also rw)

assume h : PUse P as hypothesis h now and prove P later (also have)

More examples:

enum And[A : Prop, B : Prop] : Prop {
  Conj(A, B)
}

lemma and_comm[A : Prop, B : Prop] : (And[A, B]) -> And[B, A] = proof {
  intros p
  destruct p
  exact Conj(p_1, p_0)
}

lemma modus_ponens[A : Prop, B : Prop] : (A, (A) -> B) -> B = proof {
  intros a f
  apply f
  exact a
}

lemma zero_ne_one : (0 : Nat) === 1 -> Int = proof {
  intros h
  destruct h
}
  • Tactics are just another way to build proof terms; the result is the same as a hand-written term.
  • destruct on an impossible equality (such as 0 === 1) leaves no goals.
  • There are no automation tactics such as simp, omega, or auto.

Traits

trait Shape {
  area(Self) -> Int
  name(Self) -> String
}

trait Solid : Shape {                          // supertrait
  volume(Self, Int) -> Int
}

struct Square {
  side : Int
}

impl Shape for Square with area(self) { self.side * self.side }
impl Shape for Square with name(self) { "square" }
impl Solid for Square with volume(self, depth) { self.area() * depth }

fn[S : Shape] describe(s : S) -> String {
  "\{s.name()} with area \{s.area()}"
}

fn[S : Solid] describe_solid(s : S) -> String {
  describe(s) + ", volume \{s.volume(2)}"     // supertrait methods are available
}

fn main {
  let sq : Square = { side: 2 }
  println(describe_solid(sq))
}
  • Declaration: trait Name : Super1 + Super2 { method(param types) -> result }. The first parameter of a method is usually Self. Generic methods are written fn[T] m(…).
  • Implementation: impl Tr for T with m(params) { … }, one per method. Generic instances: impl[T : Show] Show for Array[T] with to_string(self) { … }.
  • Bounds: fn[T : Tr]; multiple bounds are written [T : Eq + Show].
  • Calls: x.m() or Tr::m(x).
  • Instance search: the instances for bounds are filled in by the checker. It first looks at local bounds (and their supertraits), then at global instances (including generic instances).

Bounds and implicit parameters

[T : Add] and [n : Nat] are written the same way; they are told apart by the name to the right of the colon:

  • If the right side is a trait (or several traits joined by +), this is a bound: T is a type (its kind is determined by the trait’s Self: Type for Add, [T] -> Type for Monad), and each trait adds an instance parameter that the checker fills in automatically. Read it as “a type T that implements Add”.
  • If the right side is a type, this is an ordinary implicit parameter: n is a value of type Nat, as in fn[T, n : Nat] Vector::head(…).

Traits and types share one namespace and cannot have the same name, so there is no ambiguity. Note:

  • This rule applies only inside [...]. An explicit parameter (x : Add) is checked as a type and is an error: there are no MoonBit trait objects &Add.
  • Local names take precedence: if an enclosing parameter has the same name as a trait, the right side of the colon refers to that parameter.
  • Multiple bounds must have the same kind (the kind of T is taken from the first trait); [M : Monad + Show] is an error.

Default methods

A method declared with = _ in a trait has a default implementation, given by impl Tr with m(…) { … } (without for); an instance that does not implement it uses the default. impl Tr for T may implement no method at all.

trait Describe {
  name(Self) -> String
  describe(Self) -> String = _
}

impl Describe with describe(self) {
  "<" + self.name() + ">"
}

struct Dog {
  age : Int
}

impl Describe for Dog with name(_) {
  "dog"
}

fn main {
  let d : Dog = { age: 3 }
  println(d.describe())
}

derive

Write derive(Show, Eq, Compare) after an enum or a struct and the checker generates the instances:

enum Tree[T] {
  Leaf
  Node(Tree[T], T, Tree[T])
} derive(Show, Eq, Compare)

struct Point {
  x : Int
  y : Int
} derive(Show, Eq)

fn main {
  let t : Tree[Int] = Node(Leaf, 1, Leaf)
  println(t)                      // Node(Leaf, 1, Leaf)
  println(t == t)                 // true
  println(Leaf.compare(t))        // -1
  let p : Point = { x: 1, y: 2 }
  println(p)                      // {x: 1, y: 2}
}
  • Show: constructors as C(x, y), structs as {x: 1, y: 2}, fields with their own to_string.
  • Eq: the same constructor with equal fields.
  • Compare: by constructor, in declaration order, then by fields from left to right. Compare needs Eq, so write derive(Eq, Compare).
  • Hash: the position of the constructor and the hashes of the fields.
  • ToJson, FromJson, Debug: derived by MoonBit itself, so the type must be #mbt; the generated MoonBit declaration has derive(ToJson, @json.FromJson, Debug) and the MoonBit++ instances call these MoonBit methods (so they run in compiled programs only). FromJson needs moonbitlang/core/json among the imports, and the Debug instance moonbitlang/core/debug (without it, Debug is derived on the MoonBit side only). The format is MoonBit’s: Rgb(1, 2, 3) is ["Rgb",1,2,3], a struct is an object.
  • Type parameters get the same bound: enum Tree[T] derive(Eq) generates impl[T : Eq] Eq for Tree[T].
  • Only types with type parameters alone are supported: indexed types, enums whose constructors have a return type (GADTs) and structs with explicit parameters are not.
  • If the type of a field has no instance of the trait, the error is reported on the line of the derive.

See examples/derive.mbtpp for a complete example.

Higher-Kinded Traits and Monads

Self can be a type constructor. Monad in the Prelude:

trait Monad(Self : [T] -> Type) {
  fn[T] pure(T) -> Self[T]
  fn[T, U] bind(Self[T], (T) -> Self[U]) -> Self[U]
}

Option and List have Monad instances.

monad blocks

fn[M : Monad, T, U, V] lift2(f : (T, U) -> V, m : M[T], n : M[U]) -> M[V] {
  monad {
    let t <- m
    let u <- n
    Monad::pure(f(t, u))
  }
}

fn[M : Monad, T, U, V] lift2_inline(f : (T, U) -> V, m : M[T], n : M[U]) -> M[V] {
  monad {
    Monad::pure(f(<- m, <- n))
  }
}

fn main {
  println(lift2((a, b) => a + b, Some(1), Some(2)))
  println(lift2_inline((a, b) => a + b, Some(1), None))
  let xs : List[Int] = Cons(1, Cons(2, Nil))
  let ys : List[Int] = Cons(10, Cons(20, Nil))
  println(lift2_inline((a, b) => a * b, xs, ys))
}
  • let x <- m binds the result of m; the statements after it go into the bind callback.
  • <- m inside an expression binds in place, from left to right.
  • The Monad instance a monad { … } block uses is inferred from the expected type or from the expressions inside it.

Trait Objects

&Tr is “a value of some type that implements Tr”, as with MoonBit’s trait objects:

trait Shape {
  area(Self) -> Double
}

struct Circle {
  r : Double
}

struct Square {
  side : Double
}

impl Shape for Circle with area(self) { 3.0 * self.r * self.r }
impl Shape for Square with area(self) { self.side * self.side }

fn total(shapes : Array[&Shape]) -> Double {
  let mut s = 0.0
  for x in shapes {
    s = s + x.area()
  }
  s
}

fn main {
  let c : Circle = { r: 1.0 }
  let q : Square = { side: 2.0 }
  println(total([c, q]))               // 7
  let things : Array[&Show] = [1, "two", Some(3)]
  for t in things {
    println(t)
  }
}
  • Packing: where an &Tr is expected (a type annotation, a parameter, an array element), a value whose type has an instance of Tr is packed automatically.
  • Calls: x.m(...) calls the method of the packed instance; &Tr itself has an instance of Tr (and of its supertraits), so an &Show works with println and with functions bounded by Show.
  • Object safety: as in MoonBit, Self must be a type, and every method (supertraits’ included) mentions Self only in its first parameter and is not generic. &Eq is not allowed (op_equal(Self, Self)), nor is &Monad.
  • Representation: &Tr is the dependent struct { ty : Type; inst : Tr(ty); val : ty }, generated on first use.

Interoperating with MoonBit

A MoonBit++ &Tr can be passed for an &Tr parameter of an imported function (such as inspect(&Show, content?) of moonbitlang/core/prelude) when Tr is a MoonBit trait (a Prelude trait that is MoonBit’s, or an imported trait): in the compiled program it is wrapped in a MoonBit value whose impl calls the MoonBit++ instance. For example, a type with its own Show can be compared by MoonBit’s inspect.

Imported functions that return an &Tr cannot be compiled yet.

Mutable State and Loops

fn sum_to(n : Int) -> Int {
  let mut acc = 0
  for i = 1; i <= n; i = i + 1 {
    acc = acc + i
  }
  acc
}

fn find_first(xs : Array[Int], p : (Int) -> Bool) -> Int {
  for x in xs {
    if p(x) {
      return x
    }
  }
  -1
}

fn main {
  println(sum_to(100))
  println(find_first([1, 5, 8, 11], x => x % 2 == 0))
  let mut i = 0
  while true {
    i += 1
    if i > 5 {
      break
    }
  }
  println("i = \{i}")
  let arr = Array::make(3, 0)
  arr[1] = 42
  for k in 0..<3 {
    print(arr[k])
    print(" ")
  }
  println("")
}
  • Mutable variables: let mut x = e, assignment x = e, and +=, -=, *=, /=.
  • Loops: while c { … }; C-style for i = 0; i < n; i = i + 1 { … }; for x in xs { … } iterates over an array; for k in a..<b and for k in a..=b iterate over a range.
  • break and continue apply to the innermost loop; return returns from the current function, and inside a lambda it returns only from the lambda.
  • for i, x in xs gives the index and the element.
  • Loops are expressions: break e ends the loop with the value e; when the loop ends normally, its value is the nobreak { … } block:
fn find(xs : Array[Int], v : Int) -> Int {
  for i, x in xs {
    if x == v {
      break i
    }
  } nobreak {
    -1
  }
}

fn main {
  println(find([5, 7, 9], 9))
}
  • Labels: outer~: for … names a loop; break outer~ and continue outer~ in an inner loop apply to it.
  • loop: loop a, b { pattern => … } matches the values of the loop with arms; the value of an arm ends the loop, and continue x, y goes on with new values:
fn sum(n : Int) -> Int {
  loop n, 0 {
    0, acc => acc
    k, acc => continue k - 1, acc + k
  }
}

fn main {
  println(sum(10))
}
  • defer e: runs e when the enclosing block is left, normally or by return, break, continue or an error.
  • Arrays are mutable: xs[i] = v, xs.push(x).

Interaction with type checking

Functions that use let mut, assignment, loops, raise, or try are run during type checking, as the interpreter would run them: if the run finishes, the call is replaced by its result; if it cannot finish, the whole call stays folded, like a constant.

fn sum_to(n : Int) -> Int {
  let mut i = 0
  let mut acc = 0
  while i < n {
    i = i + 1
    acc = acc + i
  }
  acc
}

fn inc(x : Int) -> Int {
  let mut y = x
  y = y + 1
  y
}

lemma s10 : sum_to(10) === 55 = Refl
lemma inc_x[x : Int] : inc(x) === x + 1 = Refl

fn main {
  let v : Array[Int] = Array::make(sum_to(3), 0)
  println(v.length())
}
  • The run finishes when every decision can be made: for example with concrete arguments, or, like inc(x), when no decision is needed. Errors reach their try as usual, and output such as println is skipped (it does not change the result).
  • The call stays folded when a decision depends on an unknown value (if x < 0 in abs(x), where x is a variable); when an error escapes the function; when the function uses an array (arrays are mutable), an imported MoonBit function or an async function; or when a lambda captures a let mut variable. The result could then depend on more than the arguments.
  • So general properties over variable arguments, such as “for all n, sum_to(n) * 2 == n * (n + 1)”, still cannot be proved this way.
  • A loop that does not terminate keeps the checker running until the time limit of the definition.

Error Handling

suberror DivError {
  DivError(String)
}

fn div(a : Int, b : Int) -> Int raise DivError {
  if b == 0 {
    raise DivError("division by zero")
  }
  a / b
}

fn main {
  let r = try div(10, 0) catch {
    DivError(msg) => {
      println("caught: " + msg)
      0
    }
  }
  println(r)
  println(try? div(10, 2))      // Ok(5)
}
  • Error types: suberror Name { C(…) }, or the single-constructor shorthand suberror Name(String).
  • Declaration: function type -> T raise E; raise without a type means Error (any error).
  • Raising: raise e.
  • Catching: try e catch { pattern => … }. Arms match on the error’s constructor; errors that match no arm keep propagating outward.
  • try? e: produces a Result[T, Error] instead of raising.
  • fail(msg) in the Prelude raises Failure(msg).

Like functions with mutable state, functions that use raise and try are run during type checking, and stay folded when the run cannot finish (see Mutable State and Loops).

catch without try, and noraise

suberror Oops {
  Oops(Int)
}

fn risky(n : Int) -> Int raise Oops {
  if n < 0 {
    raise Oops(n)
  } else {
    n * 2
  }
}

fn safe(n : Int) -> Int {
  risky(n) catch {
    Oops(k) => k
  }
}

fn describe(n : Int) -> String {
  try risky(n) catch {
    Oops(k) if k < -5 => "very bad"
    _ => "bad"
  } noraise {
    v => "ok \{v}"
  }
}

fn main {
  println(safe(-3))
  println(describe(4))
  println(describe(-9))
}
  • e catch { … } is the same as try e catch { … }; catch must be on the same line as e.
  • noraise { pattern => … } handles the result when no error was raised. Errors raised in the catch and noraise arms are not caught by the same try.
  • catch arms can use or-patterns, as and guards.

async functions

MoonBit++ supports MoonBit’s async functions:

async fn twice(f : async (Int) -> Int, x : Int) -> Int {
  f(f(x))
}

async fn inc(x : Int) -> Int noraise {
  x + 1
}

async fn main {
  let g = async fn(x : Int) -> Int { inc(x) * 2 }
  println(twice(g, 1))
  println(twice(x => inc(x), 5))
}
  • Syntax: top-level and local functions are written async fn name(…), anonymous functions async fn(…) { … }, and function types async (A) -> B.
  • Errors: as in MoonBit, an async function may raise any error by default (like raise Error). raise E restricts the error type, and noraise says it does not raise.
  • Calls: an async function can only be called from an async function. A lambda (including x => …) checked against an async function type is async, like the second argument of twice above. A synchronous function can pass an async function around as a value, but cannot call it.
  • async fn main: the entry point can be async.
  • Interpreter: moonpp run runs async functions synchronously, one after another, without concurrency. Imported MoonBit async functions, like other imported functions, can only be called once compiled.

Using moonbitlang/async

Add the dependency with moonpp add moonbitlang/async and import it in the package’s moon.pkg to use its task groups, timers and IO:

// requires moonbitlang/async
async fn tick(name : String, n : Int, delay : Int) -> Unit {
  for i = 0; i < n; i = i + 1 {
    @async.sleep(delay)
    println(name + " " + i.to_string())
  }
}

async fn main {
  @async.with_task_group(fn(g) {
    g.spawn_bg(fn() { tick("a", 3, 30) })
    g.spawn_bg(fn() { tick("b", 2, 45) })
  })
  println("done")
}

b 0
a 1
b 1

done

async is a keyword, but it can still be a package alias: @async.sleep.

Compilation

  • Async functions are only compiled to native MoonBit code, because functions in the uniform representation are synchronous. Their signature and body must be in the native fragment; otherwise compilation fails and names the first term that is not, with the same rules as #mbt functions.
  • Async functions can also only be used by native code. If code in the uniform representation refers to an async function, for example a synchronous function outside the native fragment that returns an async lambda, compilation fails.
  • async fn main compiles to MoonBit’s async fn main, and #mbt async fn is exported as pub async fn.

moon.pkg

  "moonbitlang/x/encoding/percent",
  "moonbitlang/core/string" @str,

  "is-main": true,
)
  • The import block lists the MoonBit packages the package imports. @alias is optional and defaults to the last segment of the path.

Check order

The files of a package are checked one after another in lexicographic order of file name. Names can refer to each other (a function can call one defined later), but computation during type checking can only use function bodies that have already been checked: if a proof in facts.mbtpp needs to compute a function defined in shapes.mbtpp, shapes.mbtpp must be checked first. Use "mbtpp-order" to specify the order:

options(
  "is-main": true,
  "mbtpp-order": [ "shapes.mbtpp" ],
)

The listed files are checked first (in the listed order), and the remaining files follow in lexicographic order. In the old moon.pkg.json format, write "mbtpp-order": [ "shapes.mbtpp" ]. moon ignores this option, and moon fmt preserves it.

If an error may have been caused by the check order, moonpp gives a hint:

src/main/facts.mbtpp:1:47: error: type mismatch
  expected: Shape::area(Rect(3, 3)) === 9
  actual:   ?94 === ?94
hint: Shape::area is defined in src/main/shapes.mbtpp, which is checked after
src/main/facts.mbtpp, so its definition could not be used here; the error may
come from that. … list it in the package's moon.pkg: options("mbtpp-order": [ "shapes.mbtpp", ... ])

Old format

The old moon.mod.json and moon.pkg.json files can still be read. However, newer versions of moon no longer accept moon.mod.json, so when you need dependency management or compilation, run moon fmt in the project root to migrate; moonpp gives a hint when this happens.

How it works

moonpp reads the package’s .mbti interface file and translates its items into MoonBit++ declarations:

  • Functions become external constants: during type checking they have only a type and are never unfolded.
  • Types and traits become the corresponding MoonBit++ declarations (see Type Mapping and Skipped Items).

The interpreter cannot run imported functions; reaching one reports “cannot run the imported MoonBit function … in the interpreter”. To actually call them, run the compiled program: moonpp run --compiled (see Calling MoonBit Functions).

Re-exports

The types and functions of pub using @q {type T as U} can be used under the package’s own name (@p.U):

  • when @q is @builtin or is imported too, @p.U is @q.T (the same type);
  • otherwise @p.U is an opaque type.

The traits of @builtin (pub using @builtin {trait Show}) are the Prelude’s; other trait re-exports are not imported.

async functions are imported as MoonBit++ async functions, and so are async function types in parameters (see async Functions); the nocancel mark is ignored.

Skipped items

The following items are skipped; moonpp check --verbose lists them:

  • impls of traits that are neither Prelude traits nor imported traits (e.g. @debug.Debug when moonbitlang/core/debug is not imported);
  • #deprecated items;
  • trait re-exports (except those of @builtin), and re-exported functions whose package is not imported.

Compiling to MoonBit

The compiler translates the type-checked program into MoonBit. moonpp build and moonpp run --compiled use it; “Compile to MoonBit” in the Playground shows the result directly.

Two translations are mixed:

Native translation

A function whose parameters and result are native types, and whose body is in the first-order fragment, is translated into an ordinary (possibly generic) MoonBit function. The native types are:

  • Int, Double, Bool, Char, String, Unit;
  • type parameters and function types;
  • data types whose parameters are all types and whose fields are all native types.

Indices and erased fields disappear, for example:

enum Vector[T] : Nat -> Type { Nil : …; Cons[n : Nat](T, Vector[T](n)) : … }
// compiles to
enum E_Vector[T0] { Nil; Cons(T0, E_Vector[T0]) }

#mbt types use their own names instead of E_… (see #mbt Types and Traits).

Uniform representation

Everything else (type-level computation, GADT refinement, non-#mbt traits, etc.) uses the uniform representation Value. It is an extensible enum (MoonBit’s extenum) in the runtime, with fixed variants VInt, VFun, and so on; each generated file uses extenum Value += { … } to add the constructors of its own data types. Indices and erased fields do not appear, and fields are Value. For example, the GADT in basic.mbtpp:

enum Exp : [T] -> Type {
  IntLit(Int) : Exp[Int]
  Add(Exp[Int], Exp[Int]) : Exp[Int]
  If[T](Exp[Bool], Exp[T], Exp[T]) : Exp[T]
  …
}

compiles in basic.mbt to

extenum Value += {
  K_Exp_IntLit(Value)
  K_Exp_Add(Value, Value)
  K_Exp_If(Value, Value, Value)
  …
}

The match in eval is native:

fn f19_exp_eval(self : Value) -> Value raise {
  match self {
    K_Exp_IntLit(n) => n
    K_Exp_Add(lhs, rhs) => VInt(as_int(f19_exp_eval(lhs)) + as_int(f19_exp_eval(rhs)))
    …
  }
}

The result type of eval varies with the index (the IntLit branch returns Int, the BoolLit branch returns Bool), which MoonBit’s type system cannot express, so its result is still Value. Runtime support (apply, primitives, the dynamic pattern matcher) lives in the generated mbtpp_runtime.mbt; it gets constructor names and fields (for display and equality) from decoders that each file registers in fn init. The two kinds of code convert values at their boundary.

Because Value can be extended from other files and other packages, this representation also suits separate compilation of multiple MoonBit++ packages in the future.

Erasure

  • Type parameters are always erased.
  • Other implicit parameters and implicit constructor fields are erased when they are used only in types.
  • Proofs are always erased: parameters and fields whose type is a proposition (implicit or not), lets of proofs and calls of lemmas produce no code, and lemmas themselves are not generated; a match on a proof runs its first arm (a match on a proof of an empty proposition becomes an abort). So a #mbt fn can have proof parameters, like fn get(xs : Array[Int], i : Int, p : i < n), and the exported MoonBit function does not have them.

Performance

A fib program runs about 40 times faster when compiled (7.85 s interpreted, 0.18 s compiled). Before constructors became native variants of Value, data in the uniform representation was VCon(constructor name, field array) and matching compared strings; with native variants, evaluating an Exp tree with 2^18 leaves 20 times dropped from 2.65 s to 1.26 s.

#mbt Types and Traits

Putting #mbt before an enum, struct, or trait declares that it corresponds directly to a MoonBit type or trait. Compiled native code uses these MoonBit types directly, and MoonBit functions can take them without conversion.

#mbt
enum Tree[T] {
  Leaf
  Node(Tree[T], T, Tree[T])
}

#mbt
struct Pt {
  x : Int
  y : Int
}

#mbt
trait Size {
  size(Self) -> Int
}

impl Size for Int with size(self) { self }
impl Size for Pt with size(self) { self.x + self.y }
impl[T : Size] Size for Tree[T] with size(self) {
  match self {
    Leaf => 0
    Node(l, x, r) => l.size() + x.size() + r.size()
  }
}

fn main {
  let t : Tree[Pt] = Node(Leaf, { x: 1, y: 2 }, Leaf)
  println(t.size())
}

The output includes pub(all) enum Tree[T0], pub(all) struct Pt, pub(open) trait Size, and impl[T0 : Size] Size for Tree[T0].

#mbt does not change type checking or interpretation; it only affects compilation. Its conditions are checked during type checking, and an error is reported if they are not met.

#mbt types

  • Only type parameters, no indices; not a proposition and not a suberror; constructors have no implicit fields.
  • Field types are MoonBit types: Int, Double, Bool, Char, String, Unit, type parameters, #mbt types, and function types between them. Arrays are not supported yet.
  • Generated type and constructor names must start with an uppercase letter and must not clash with existing names such as Value or Option.

#mbt(“name”)

Maps to an existing MoonBit type or trait; no declaration is generated. Option and Result in the prelude are #mbt("Option") and #mbt("Result"). pub(all) types and pub(open) traits imported from .mbti automatically get #mbt("@pkg.T") (when the conditions hold).

#mbt traits

  • Self : Type; supertraits are also #mbt.
  • Methods are not generic; their parameters and results are MoonBit types (Self may appear).
  • All methods in the generated MoonBit trait are marked raise (compiled code implements control flow with errors).
  • In native code, a bound [T : Size] becomes MoonBit’s fn[T0 : Size], and a method call becomes Size::size(x).

Instances of #mbt traits

  • Only type parameters and #mbt bounds; Self is a MoonBit type (not just a type parameter).
  • MoonBit’s orphan rule applies: existing traits (#mbt("…") or imported) can only be implemented for types generated by this program.
  • Read-only (pub) traits cannot be implemented.
  • Instances whose methods are in the native fragment generate a MoonBit impl.

Finding declarations that could be #mbt

#mbt is an explicit contract; the compiler never adds it on its own. But moonpp check examines enums, structs, traits, and functions marked pub without #mbt, and gives a hint for each one that meets the #mbt conditions:

src/main/shapes.mbtpp:2: hint: pub type Shape could be #mbt (it would be a MoonBit type)
src/main/shapes.mbtpp:23: hint: pub trait Area could be #mbt (it would be a MoonBit trait)
src/main/shapes.mbtpp:41: hint: pub fn norm1 could be #mbt (it would be exported as a MoonBit function)
  (`moonpp fix` adds #mbt to them)
ok: src/main

moonpp fix inserts a #mbt line above these declarations and re-checks the package; if the check fails, it restores the original files.

  • Only pub declarations are considered: pub has no other meaning in MoonBit++, so here it signals “intended for MoonBit”.
  • Types and traits are judged together: several mutually referring types can become #mbt at once.
  • A function needs a translatable signature (assuming the hinted types are annotated) and a body in the native fragment (the same check the compiler does).
  • Indexed types, types and functions that mention them, and lemmas are never hinted.

#mbt Functions

Functions can be marked #mbt too: each is compiled to a public MoonBit function of the same name, which MoonBit code can call directly.

#mbt
enum Tree[T] {
  Leaf
  Node(Tree[T], T, Tree[T])
}

#mbt
fn[T] insert(t : Tree[T], x : T, lt~ : (T, T) -> Bool) -> Tree[T] {
  match t {
    Leaf => Node(Leaf, x, Leaf)
    Node(l, y, r) =>
      if lt(x, y) {
        Node(insert(l, x, lt~), y, r)
      } else {
        Node(l, y, insert(r, x, lt~))
      }
  }
}

#mbt
fn[T] Tree::depth(self : Tree[T]) -> Int {
  match self {
    Leaf => 0
    Node(l, _, r) => {
      let a = l.depth()
      let b = r.depth()
      1 + (if a > b { a } else { b })
    }
  }
}

fn main {
  let mut t : Tree[Int] = Leaf
  for i = 0; i < 6; i = i + 1 {
    t = insert(t, i * 7 % 10, lt=(a, b) => a < b)
  }
  println(t.depth())
}

The output:

pub fn[T0] insert(t : Tree[T0], x : T0, lt~ : (T0, T0) -> Bool raise) -> Tree[T0]
pub fn[T0] Tree::depth(self : Tree[T0]) -> Int32

(moon fmt writes MoonBit’s Int as Int32.)

Signature (checked during type checking)

  • Implicit parameters can only be type parameters [T]; bounds can only be #mbt traits on type parameters, and a bounded type parameter must appear in the parameters or the result.
  • Parameters and results are MoonBit types; proof parameters (whose type is a proposition) are erased and do not appear in the MoonBit function.
  • x~ and x? parameters are supported; default values are not.
  • Methods can only belong to #mbt types generated by this program.
  • main cannot be marked #mbt.
  • #mbt("name") sets the function’s name in MoonBit.

Body (checked during compilation)

The body must be in the native fragment; otherwise compilation fails and points to the first expression that cannot be natively translated, for example:

#mbt fn f cannot be compiled to MoonBit: its body is not in the native fragment:
in `println(x)`, println has no native signature (a type without a MoonBit type,
or a bound that is not #mbt)

raise

A function that does not declare raise does not raise in MoonBit either; runtime failures inside it (such as an incomplete match) become abort. A function that declares raise E is raise in MoonBit.

Using Compiled Code from MoonBit

#mbt functions, types, and traits are public after compilation, so MoonBit code can use them.

For example, after compiling the program in #mbt Functions, add a MoonBit test file export_wbtest.mbt to the main/ directory of the generated project:

test "exported functions" {
  let t = insert(Tree::Leaf, 3, lt=(a, b) => a < b)
  inspect(t.depth(), content="1")
}

Then run moon test in the generated project.

Other MoonBit projects can also reference the generated project through a workspace (moon.work).

Currently the output is always a main package (with a main function); standalone library packages cannot be generated yet.

Known Limitations

Language

  • No termination checking or strict positivity checking (by design): you can “prove” false propositions.
  • No resumable algebraic effects, and no automation tactics such as simp, omega, or auto.
  • Recursive local functions cannot use the let mut variables around them.
  • A match with array patterns is not checked for coverage and does not refine types.
  • Map is implemented in MoonBit++ by the Prelude (in insertion order, with linear lookups); it is not MoonBit’s Map, so imported functions taking or returning a MoonBit Map cannot be called.
  • There are no BigInt literals (1N), Int16 or UInt16; Float only has its operators, comparisons and conversions.
  • When functions with mutable state are run during type checking, calls that use arrays, imported functions or lambdas capturing let mut variables are not run (see Mutable State and Loops).
  • Time limits are measured in wall-clock time, so a file may time out on a slower machine (see Time limits).
  • Structs have no mutable fields, and there are no struct patterns.
  • Traits have no default methods.

Imports

  • The interpreter cannot run imported MoonBit functions; they can only be called after compilation.
  • The interpreter runs async functions synchronously, without concurrency; async functions are only compiled to native code (see async Functions).
  • Generic impls, trait objects, and similar items in imported packages are not imported (see Type mapping and items not imported).

Compiler

  • Arrays are not native types in native code: signatures containing arrays use the uniform representation and cannot be #mbt.
  • Values are converted by value between the uniform representation and native code, so frequently passing large data across the boundary is slow.

Tooling

  • The generated project is always a main package; library packages cannot be generated.
  • Requires a recent moon (one that uses moon.mod / moon.pkg).
